# Boccia Hub: 라벨러·트래커 모니터링, 원격 명령, 작업 수집, 버전 관리 (2026-10-19)

네 번째 앱. 라벨러·트래커를 쓰는 PC(joonyeon 등)에서 무슨 일이 있는지 이 PC에서 보고, 명령을 보내고, 내보낸 작업을 받아 오고, 새 버전을 나눠 주고 되돌린다.
2026-10-15~19에 joonyeon의 트래커·라벨러 문제를 Taildrop·원격 데스크톱·파일 주고받기로 풀면서 사용자가 요청한 것:
"라벨러 누가 실행하면 중앙 서버에 붙고 작업 하나하나 다 모니터링하고 cli로 명령도 보낼 수 있게", "트래커도 버전 관리할 필요성이 있거든 모니터링이랑".

## 결정 (2026-10-19 사용자)

1. **목적**: 원격 문제 해결, 작업 진행 관리, 원격 작업 지시, 작업 수집, 버전 관리·롤백. 대상은 라벨러와 트래커(트레이너는 나중에).
2. **트레이너와 분리한 앱**이다. 트레이너는 학습만 하고, 허브 저장소의 내보내기를 폴더로 읽는다.
3. **허브는 이 PC**(mark-hong-pc)에서 돈다. 로그인하면 뜨고, **항상 켜져 있지는 않다**(끄면 라벨러·트래커는 혼자 돌고, 올릴 것은 보관했다가 다음에 올린다).
4. 라벨러·트래커는 **허브가 켜져 있을 때만** 붙는다.
5. **파일은 허브가 직접 보관**한다(`D:\Boccia Hub\`). S3·R2 같은 외부 저장소는 나중에.
6. **작업자 이름 + PC**로 구분한다. 처음 켤 때 이름을 한 번 묻는다.
7. 보내는 내용은 **사람 동작까지**(장면 확인·보류, 공 추가·삭제·수정).
8. 명령은 **상태·로그·점검 / 새 버전 / 작업 / 설정·알림**과 **화면 캡처**.
9. 작업 수집은 라벨러의 **내보내기**를 그대로 쓴다. 허브에 붙어 있으면 내보내기 창에 "허브로 올리기"가 켜지고, 허브의 "가져오기"는 그 라벨러에 내보내기를 시키는 것이다. 라벨은 항상, **이미지는 허브에 없는 것만** 올린다.
10. 패치 파일을 따로 만들지 않는다. 버전 = 배포 폴더 + 목록(파일별 해시). 받는 쪽이 다른 파일만 받는다. 버전은 전부 보관하고 이전 버전 보내기가 곧 롤백이다.
11. 화면은 **HTML**(밝은 바탕, 설명 문장 없이 라벨·숫자·버튼만, 모서리 5px, 아바타 없음). 허브(Python)가 띄우고, 창은 Windows의 Edge 앱 모드로 연다. 휴대폰·맥북 브라우저에서도 같은 화면.
12. 언어: 허브는 Python(표준 라이브러리만, 이 PC에만 있으면 됨), 라벨러·트래커 쪽 접속 코드와 패처는 C++. Rust는 공유 코드가 없는 독립 도구에나 쓴다.

## 범위 밖

- 외부 저장소(R2·S3). 폴더 구조를 그대로 옮길 수 있게만 해 둔다.
- 원본이 이 PC에 있는 촬영의 이미지 생략(허브가 직접 만들기). 2단계.
- 트레이너 버전 관리·모니터링. 같은 클라이언트를 붙이면 되므로 뒤에.
- 라벨러·트래커 화면의 HTML 전환.
- tailnet 밖 접속과 인증(토큰). 필요해지면 넣는다.

다른 PC 라벨러·트래커 ──┼─ Tailscale ─→ 이 PC: Boccia Hub (Python, 8790) ←─ 창(Edge 앱 모드) · 브라우저 · boccia-hub CLI
이 PC 라벨러·트래커   ──┘                      └ D:\Boccia Hub\ (exports · images · releases · screens · logs)
                                                └ 트레이너는 exports\를 폴더로 읽는다

- 주소 `mark-hong-pc.tail68c059.ts.net:8790`. Tailscale MagicDNS 이름이라 IP가 바뀌어도 그대로다. 허브는 Tailscale 주소와 localhost에만 연다.

## 앱이 붙는 방식 (라벨러·트래커 공통, `src/hub_client.cpp`)

| 때 | 앱이 하는 일 |
| --- | --- |
| 10초마다 | `GET /ping`. 응답이 없으면 아무것도 안 함 |
| 응답이 오면 | **등록**: 앱 종류, 작업자 이름, PC 이름, Windows 계정, 버전, 실행 장치(GPU/CPU·CUDA), 그리고 앱별 요약(아래). 그다음 보관함을 비우고 로그에서 **마지막으로 보낸 시각 이후 줄**을 보낸다 |
| 붙어 있는 동안 | 상태가 바뀌면 `POST /status`, 일이 생기면 `POST /events`(묶어서 1초마다). 명령은 `GET /commands?wait=25`로 기다렸다 받는다 |
| 꺼질 때 | `POST /bye`(0.5초만 기다림). 허브는 바로 떨어짐으로 표시한다(2026-10-20) |
| 요청이 실패하면 | 떨어진 것으로 보고 10초 노크로 돌아간다 |

**보관함** `<앱>\outbox\`: 허브가 없을 때 올릴 것(내보내기 결과, 가져오기 묶음, 화면 캡처 결과)을 둔다. 붙으면 순서대로 올리고 지운다.
떨어져 있던 동안의 동작은 **로그 파일**(`logs\<앱>-날짜.log`)이 기록이다. 붙을 때 이어 보내므로 활동 탭이 시간순으로 채워진다.

## 명령

화면 버튼과 CLI가 같은 명령을 만든다. 허브에 쌓이고 앱이 붙어 있으면 바로, 아니면 붙을 때 순서대로 실행한다. 결과는 이벤트로 돌아온다.

| 명령 | 대상 | 앱이 하는 일 |
| --- | --- | --- |
| 로그 | 둘 다 | `logs\<앱>-날짜.log` 전체를 올린다 |
| GPU 점검 / CUDA 점검 | 둘 다 | 라벨러는 `--device-check`, 트래커는 `cuda status`와 같은 점검을 돌려 결과를 올린다 |
| 화면 | 둘 다 | 자기 창을 찍어(숨긴 점검의 캡처와 같은 방법, Windows 권한 불필요) PNG를 올린다. "5초마다"면 켜 둔 동안 반복. 창 밖은 찍지 않는다 |
| 가져오기 · 형식 | 라벨러 | 확인한 라벨을 그 형식으로 내보내고 허브로 올린다(아래). 작업 중이면 끝난 뒤 |
| 라벨 파일 백업 | 라벨러 | `labels\project.json`만 올린다 |
| 초안 다시 만들기 · 원형 검출 · 작업 중단 · 프로젝트 열기 · 실행 장치 | 라벨러 | 서랍·창·설정의 같은 기능 |
| CUDA 설치 · 보정 가져오기 · 녹화 중단 | 트래커 | 트래커의 같은 기능(`cuda install`, `data import`) |
| 알림 · 문구 | 둘 다 | 아래 막대에 문구를 띄운다(닫을 때까지) |
| 새 버전 · 버전 / 이전 버전으로 | 둘 다 | 아래 "새 버전 패치" |

CLI `boccia-hub`(이 PC): `status`, `workers`, `trackers`, `logs <이름>`, `send <이름> <명령> [값]`, `pull <이름> [yolo|coco]`, `release labeler|tracker`, `versions`, `screen <이름>`.

## 내보내기 올리기

- 라벨러 내보내기 창에 **허브로 올리기** 체크. 허브에 붙어 있을 때만 켜진다. 아니면 지금처럼 폴더로만.
- 올리는 순서: (1) manifest와 라벨 파일, (2) 이미지 해시 목록 → 허브가 **없는 것만** 답함, (3) 그 이미지만. 같은 촬영을 다시 내보내도 이미지는 한 번만 올라간다(트레이너가 같은 이미지를 해시로 한 번만 세는 규칙과 같은 기준).
- 같은 이미지인지는 **파일 내용의 SHA-256**으로 안다. 같은 프레임을 같은 방식으로 PNG로 만들면 바이트가 같다. 라벨러 버전이 바뀌어 PNG 만드는 설정이 달라지면 같은 프레임도 다른 파일이 되므로, manifest에 **원본 키**(촬영 지문 · 카메라 · 프레임 번호, 사진은 원본 파일 해시)도 적어 해시가 달라도 같은 원본 프레임이면 같은 것으로 묶는다.
- 끊기면 이어서 올린다(올린 파일 목록을 보관함에 둠). 올리는 동안 라벨러는 쓸 수 있다.
- 허브 저장: `exports\<작업자>\<날짜-시각-지문8>\`(라벨러 내보내기 폴더와 같은 모양, 이미지는 목록만) + `images\<sha256>`(한 벌).
- 트레이너는 `exports\`를 폴더로 읽어 자료 탭에 넣는다. 이미지가 덜 온 것은 manifest의 상태로 알고 "받는 중 412 / 1,180"으로 보이며 학습에는 다 온 뒤 쓴다.
- 처음 올리는 촬영 1,000장은 PNG로 1 GB쯤: Tailscale 직접 연결이면 몇 분, 중계(DERP)면 더 걸린다.

## 새 버전 패치 (라벨러·트래커 공통)

1. **등록**(이 PC): 패치 파일을 따로 만들지 않는다. `tools/collect_release.ps1`(라벨러)와 `package-tracker.ps1`(트래커)이 배포한 끝에 허브에 등록한다: 배포 폴더의 파일을 `releases\files\<해시>`에 한 벌로 두고, `releases\<앱>\<버전>\목록.json`(파일 이름·크기·SHA-256)을 만든다. 버전은 실행 파일에 박힌 빌드 시각 + git 해시(`1.6.3 · 2026-10-19 15:48 · 849e7a5`, `--version`). 메모를 적을 수 있다. 손으로 배포 폴더를 바꿨을 때는 버전 탭의 "등록" 또는 `boccia-hub release <앱>`.
2. **명령** `update <버전>`. 버전 탭에서 대상을 고른다. 기본은 "현재" 버전.
3. **앱**: 목록과 자기 파일을 해시로 비교해 다른 파일만 `<앱>\update\<버전>\`로 받고 SHA-256을 다시 확인한다. 틀리면 아무것도 바꾸지 않고 실패를 보고한다. 도는 작업이 없고 저장할 것이 없을 때 "새 버전 1.6.3 · 다시 시작" 창을 띄운다(다시 시작 / 나중에). 허브가 "바로"를 지정하면 안전한 시점에 자동. 그다음 `boccia_update.exe <앱 폴더> <update 폴더>`를 띄우고 종료한다.
4. **패처 `boccia_update.exe`**(배포 폴더 루트, 세 앱 공용, C++ 작은 프로그램): 앱이 끝날 때까지 기다린 뒤 파일마다 현재 파일을 `update\backup\<이전 버전>\`으로 옮기고 새 파일을 제자리로(같은 드라이브 이동), 앱을 실행한다. 10초 안에 죽거나 안 뜨면 backup으로 되돌리고 이전 버전을 실행한다. 결과는 `update\result.json`에 남기고 앱이 다음에 붙을 때 보고한다. `data\`는 건드리지 않는다. backup은 마지막 2개 버전만 남긴다.
5. 패처 자체는 앱이 바꾼다(패처는 실행 중이 아닐 때).

**버전 관리와 롤백**
- 등록한 버전은 전부 남긴다. 파일은 해시로 한 벌이라 버전 하나에 바뀐 파일 크기만 든다(보통 exe 3.5 MB). `releases\<앱>\index.json`에 목록과 상태(현재 / 보통 / 철회).
- 앱의 적용 절차는 버전을 모르고 목록과 해시만 보므로, **이전 버전 보내기가 곧 롤백**이다. "이전 버전으로" 명령은 앱의 backup에서 내려받기 없이 되돌린다.
- 문제 있는 버전은 **철회** 표시: 더는 보내지지 않고, 그 버전을 쓰는 PC는 목록에 주황으로 보인다.
- PC마다 어느 버전을 언제 적용했고 결과가 어땠는지(적용 / 되돌림 · 이유)를 허브가 남긴다. 상세 원격 탭 "버전" 줄.

## 보안

지킬 것은 데이터(공 라벨·이미지·화면·로그는 민감하지 않다)가 아니라 **명령·업데이트 통로**다: 허브에 명령을 넣을 수 있으면 작업자 PC에 아무 실행 파일이나 심을 수 있다.

- **제어면 분리**: 명령을 만드는 쪽(화면·CLI·버전 등록)은 localhost와 Tailscale에서만 받는다. 앱이 쓰는 쪽(등록·상태·이벤트·업로드·명령 받아 가기)만 밖으로 열 수 있다. 밖에서 온 요청으로는 명령을 만들 수 없다.
- **작업자별 토큰**(32바이트 난수, 작업자 탭의 "초대 코드"로 전달, 앱 설정에 한 번 저장): 등록·업로드·명령 받기에 필요. 새면 그 작업자 것만 바꾼다. 1단계에 넣는다.
- 파일 교체는 목록의 SHA-256이 맞을 때만, 목록은 이 PC에서 등록한 것만. 업로드 파일은 해시 이름으로만 저장한다(경로 주입 불가). 요청 크기·개수 제한.
- **Tailscale 안에서만**(2026-10-19 사용자: "테일스케일로 가자"). 허브는 Tailscale 주소와 localhost에 바인드. 연구소 PC는 **연구소 Tailscale 계정**의 tailnet에 **사전 인증 키 + 태그**(`tailscale up --auth-key …`, `tag:boccia`)로 넣어 작업자가 계정 없이 붙고 사용자 수에 안 센다. ACL로 그 태그는 허브 PC의 8790만 보게 한다. 계정 만들기·키 발급·ACL은 사용자가 관리 화면에서 하고, 그때 붙여 넣을 ACL 내용을 적어 준다. 허브 주소는 설정값이라 tailnet이 바뀌어도 코드는 그대로다. Tailscale을 못 까는 PC가 생기면 그때 **Tailscale Funnel**로 앱 쪽만 공개한다(HTTPS는 Funnel이 담당). 공유기 포트 포워딩 + DDNS는 쓰지 않는다.
- 작업자 이름은 구분용이지 인증이 아니다.

## 구현 순서

단계마다 빌드·테스트·캡처를 보여 드리고 다음으로 간다.

1. 허브 최소(등록·상태·이벤트·명령·로그 보관·화면 캡처 저장)와 CLI, 공용 클라이언트와 라벨러 연결(노크·등록·상태·이벤트·보관함·명령 받기), 작업자 이름. 이 PC의 라벨러 둘을 붙여 확인.
2. 허브 화면: 작업자 목록·상세의 활동·진행 탭, 창(Edge 앱 모드).
3. 원격 탭: 화면 캡처, 로그, GPU 점검, 작업 명령, 알림.
4. 내보내기 올리기(해시 중복 제거·이어 올리기)와 가져오기, 트레이너 자료 탭의 폴더 읽기.
5. 버전: 등록(배포 스크립트), 목록 화면, 패처 `boccia_update.exe`, 적용·되돌리기·철회·기록.
6. 트래커 연결(이벤트·명령·CUDA 설치·보정 가져오기)과 트래커 탭, 트래커 패치.
7. 문서, 배포, joonyeon에서 실제 확인.

## 확인 방법

- 클라이언트 테스트는 가짜 허브(테스트 안의 작은 서버)를 상대로 노크·등록·이벤트 묶음·명령·보관함·끊김 복구·업데이트 적용(성공·실패·되돌리기)을 본다.
- 허브 테스트는 업로드 중복 제거, 이어 올리기, 명령 큐, 배포 목록, 롤백 기록.
- 화면은 브라우저 캡처로 시안과 비교한다.
- 이 PC에서 라벨러 복사본 둘과 트래커를 허브에 붙여 목록·활동·명령·가져오기·패치·롤백을 끝까지 돌린 뒤 joonyeon에서 같은 순서로 한다.
